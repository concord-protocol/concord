# CORD-09: Blinded Mention Locators

Concord encrypts the author, mention targets, message kind, and functional tags
of a Channel message inside a CORD-01 Stream event. That is the right privacy shape,
but it leaves a background notification service unable to distinguish an
`@mention` from an ordinary message without holding the Channel key and opening
the wrap.

This CORD defines an optional, relay-indexable locator for explicit mentions.
It lets a member subscribe to mentions without publishing their Nostr pubkey on
the outer event and without giving a push service the Channel key. The cost is
metadata: a locator makes a mention-bearing wrap distinguishable from ordinary
CORD-01 traffic and linkable to other mentions of the same member within one
Stream epoch. Section 6 makes that leakage explicit.

This extension applies only to durable kind `1059` events on a Channel's Chat
Plane (CORD-03). It does not change CORD-01 encryption, signatures, binding, or
message validation. Implementations MAY omit locators entirely.

---

## 1. The locator

For one Channel Stream epoch, let:

- `conv_key` be the 32-byte CORD-01 NIP-44 self-ECDH conversation key of that
  Channel's current `group_key` (CORD-02 Appendix A.2);
- `mentioned_xonly` be the mentioned member's raw 32-byte x-only Nostr pubkey,
  not its hex or bech32 encoding.

The member's mention locator is:

```
mention_locator(conv_key, mentioned_xonly):
    HKDF-SHA256(
        ikm  = conv_key,
        salt = ∅,
        info = utf8("concord/mention-locator") || 0x00 || mentioned_xonly[32],
        len  = 32)
```

The on-wire value is the 32-byte result encoded as 64 lowercase hex
characters.

The label and byte layout above are frozen. Because `conv_key` changes with the
Channel Stream key, the locator changes on every Public-Channel Refounding and
Private-Channel Rekey. Locators from retired epochs MUST NOT be reused for the
current epoch.

## 2. Sending

An explicit mention is a kind `9` Chat rumor carrying a `p` tag whose first
value is the mentioned member's 32-byte lowercase-hex pubkey. Threaded replies
(kind `1111`) use `p` for the immediate parent author and are not explicit
mentions under this CORD. Reactions and other directed actions are likewise out
of scope.

For each distinct, well-formed `p` tag on a kind `9` rumor, a supporting sender
MAY derive the corresponding locator and add it to the outer Stream wrap:

```jsonc
{
  "kind": 1059,
  "pubkey": "<current channel stream pubkey>",
  "content": "<CORD-01 encrypted seal>",
  "tags": [
    ["p", "<random ephemeral pubkey>"],
    ["m", "<64-char blinded mention locator>"],
    ["m", "<another locator, when another member is mentioned>"]
  ],
  "created_at": 1686840217,
  "sig": "<stream signature>"
}
```

The required CORD-01 ephemeral `p` tag remains unchanged. One `m` tag is added
per distinct mentioned pubkey; duplicate locators MUST be removed. A sender
MUST NOT put the mentioned member's real pubkey or any reversible encoding of
it on the wrap.

An `m` tag is a hint, not authority. It is covered by the shared Stream
signature, which any Channel keyholder can produce, but not by the real
author's seal signature. The signed inner rumor remains the only truth about
whether the author mentioned anyone.

A sender MUST NOT add an `m` tag whose locator is not derived from a `p` tag on
the enclosed kind `9` rumor. Receivers nevertheless MUST assume a malicious
Channel member can do so and validate after opening as described in Section 4.

CORD-08 `expiration` tags, when present, remain independent of this extension.
Mention locators MUST NOT be added to ephemeral kind `21059` wraps.

## 3. Subscribing

A member that wants background notifications only for explicit mentions
derives its locator from its own x-only pubkey and the current Channel Stream's
`conv_key`, then registers this Nostr filter:

```json
{
  "kinds": [1059],
  "authors": ["<current channel stream pubkey>"],
  "#m": ["<my blinded mention locator>"]
}
```

Both terms are required. The `authors` term confines the locator to the Channel
Stream that derived it; `#m` prevents ordinary messages on that Stream from
waking the subscriber.

Notification levels map to filters as follows:

- **All messages:** subscribe to the current Stream author without `#m`.
- **Mentions only:** subscribe to the current Stream author and the member's
  `#m` locator.
- **Muted:** do not subscribe to that Stream.

On a Channel key rotation, a client MUST remove the old live-notification
filter and derive both the author and locator for the new epoch. Historical
queries may continue reading held epochs, but retired epochs MUST NOT remain in
the live mention-notification set: a replayed historical wrap must not ring as
a new mention.

A client SHOULD preserve each `(stream author, locator)` pair in one filter.
Combining many authors and locators into the same Nostr filter creates a
cross-product rather than pairwise matching. A client MAY accept that broader
hint set to meet a push service's subscription limit, but MUST still perform
the validation in Section 4.

---

## 4. Receiving and validation

Matching an `m` tag is permission to fetch and attempt to open a wrap. It is
never proof that a mention exists.

After opening the CORD-01 wrap, a receiver MUST apply the ordinary CORD-03
Channel and epoch binding checks. Before presenting the event as a verified
mention, it MUST additionally confirm all of the following:

1. the rumor is kind `9`;
2. the rumor contains a well-formed `p` tag equal to the receiver's real
   pubkey;
3. the matched outer `m` value equals the locator recomputed from the Stream
   key that opened this wrap and that pubkey.

Failure means the outer hint was false or malformed. The client MUST NOT count
it as a mention, add it to a mention inbox, or use it as authorization for any
action.

A platform may require a push event to display something before the client can
decrypt and validate it. In that case the notification MUST remain generic and
MUST NOT claim a verified author, Channel, or message preview based only on the
outer tag. This CORD reduces honest false-positive pushes; it cannot prevent a
malicious Channel member from deliberately generating one.

---

## 5. Compatibility

This is an additive extension:

- A CORD-01 reader that does not implement this CORD continues to query the
  Stream by author, ignores the unknown `m` tag, and opens the message normally.
- A supporting reader can receive messages sent by an older client normally,
  but a mentions-only background subscription will not wake for those messages
  because their wraps have no locator.
- Foreground clients that already hold and decrypt the Stream can continue
  detecting mentions from the inner rumor, regardless of whether an outer
  locator exists.

A client MUST NOT silently fall back from **mentions only** to **all messages**
when a locator is absent. Missing an unmarked background mention is the honest
compatibility failure; notifying for every opaque wrap violates the user's
chosen level and recreates notification flooding.

No capability bit is required for reading. User interfaces MAY explain that
background mention delivery depends on the sending client supporting this
CORD during the adoption period.

---

## 6. Privacy and security considerations

CORD-01 normally makes a Channel Stream wrap resemble giftwrap traffic: a fixed
opaque Stream author and a random ephemeral `p` tag reveal neither the real
author nor a recipient. An `m` tag deliberately spends some of that metadata
privacy to make relay-side filtering possible.

### What a relay or passive observer learns

- that this Stream wrap carries at least one explicit mention;
- the number of distinct locators on the wrap;
- whether two wraps in the same Stream epoch carry the same locator.

Without `conv_key`, the observer cannot test a candidate Nostr pubkey against a
locator. A Stream rekey changes both the author and every locator, so an
observer cannot link the marker across epochs from the derivation alone.

### What a push service learns

A push service receiving an identity-authorized subscription can associate the
subscriber with the locator and the watched Stream address. Blinding protects
the pubkey from relays and observers that do not see that registration; it does
not hide the mapping from the notification provider itself. Deployments that
cannot accept this disclosure MUST omit locators or use a trusted/local
notification service that holds the Channel key and filters after decryption.

### What another Channel member can do

Every Channel member holds the Stream key, can derive locators for known
pubkeys, and can sign outer wraps at the shared Stream address. A malicious
member can therefore forge an `m` hint and trigger a generic wake-up. They
cannot forge the real author's seal or make the false hint pass Section 4.
This does not give outsiders a new spam path: the filter also requires the
secret-derived Stream author.

### Optionality

Communities and clients that prioritize indistinguishable Stream traffic over
filtered background notifications SHOULD omit `m` tags. There is no mode that
simultaneously gives a content-blind relay exact mention filtering and reveals
no filterable fact about mentions; this CORD makes that trade explicit rather
than weakening encryption or publishing the recipient's real pubkey.
