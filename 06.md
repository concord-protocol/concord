# CORD-06: Rekeys and Refoundings

Non-ratcheted, asynchronous key rotation for post-removal secrecy.

**Rekeys** rotate a Channel's encryption key to cryptographically sever a removed user (or many), authorized by a valid administrator. A single-channel rekey typically follows removing someone's access to a specific channel — e.g. removing a role (`Tester`) with access to a private channel (`#testers`).

**Refoundings** are whole-Community Rekeys, rotating the base community key in addition to all relevant channels. This removes someone absolutely from a Private Community, severing even the uppermost planes.

----

## 1. Rekey Blobs - The 3303 event

Key distribution rides "Rekey Blobs": a Community-encrypted kind 3303 package delivering the fresh key to up to 80 participants per event, 60 for a base rotation whose blobs are wider (a reader accepts 120), spanning several events for a large community.

A rekey has a scope, either a **Channel** (a specific Private Channel's ID) or the **`community_root`** (a base rotation):
```
Scope       = Channel(channel_id) | community_root
id32(Scope) = channel_id[32]      | 0x00…00 (all-zeroes, never collides with a Channel ID)
```

Private Channels are independently keyed (cryptographically unrelated to the `community_root`, CORD-03), so a compromised Private Channel exposes only itself and can be rekeyed alone. A Public Channel derives its key from the `community_root`, so it has no independent rekey — it rotates only when the base does (a Refounding).

Because a rekey targets one specific key, it must name exactly which one it replaces: **Scope** binds to the blob's ciphertext (not just an outer tag), so a blob minted for one channel can never be replayed against another.

The Rekey Event:
```jsonc
{
  "kind": 1059,                          // gift wrap
  "pubkey": "<group_pk>",                // the rekey address (community_root-derived)
  "tags": [["p", "<random ephemeral pubkey>"]],   // ephemeral, like any Stream event (CORD-01)
  "content": "nip44_encrypt(conv_key, {   // seal
     "kind": 20013,
     "pubkey": "<rotator real pubkey>",
     "sig": "<rotator real signature>",    // authorship + authority actor
     "content": "nip44_encrypt(conv_key, { // rumor
        "kind": 3303,
        "pubkey": "<rotator real pubkey>",
        "content": "[ {blob}, {blob}, … ]",   // per-recipient blobs (§2)
        "tags": [
          ["scope",      "<id32(Scope) hex>"],   // all-zero hex = community_root
          ["newepoch",   "<decimal>"],
          ["prevepoch",  "<decimal>"],
          ["prevcommit", "<hex>"],
          ["chunk",      "<i>", "<n>"],          // this event is chunk i of n for the rotation
          ["vac",        "<grant eid>", "<grant version>", "<grant edition hash>"],  // the Rotator's citation (§3, Authority); absent when the owner rotates
          ["sever",      "1"]                    // OPTIONAL, base rotations only: a Severing Refounding (§3)
        ]
     })"
  })"
}
```

Each blob in the `content` array is one located, wrapped key:
```jsonc
{ "locator": "<hex>",      // where its recipient finds it (§2)
  "wrapped": "<base64>" }  // NIP-44 ciphertext under the Rotator↔recipient pairwise key
```
The wrapped plaintext is fixed-width per form, its width and the event's scope declaring the form, and NIP-44 encrypts its padded base64 (RFC 4648 §4), the width checked after decoding. A Channel rotation's blob is 72 bytes: `scope_id[32] ‖ epoch_be[8] ‖ new_key[32]`. A base rotation also carries the next epoch's Control Plane keys (CORD-02 §2): a member's blob is 104 bytes — `scope_id[32] ‖ epoch_be[8] ‖ new_root[32] ‖ new_control_pk[32]` — and a staff recipient's (CORD-04 §3) is 136, appending `new_control_root[32]`. One historical form joins these: a 72-byte *base* blob is a legacy, pre-split rotation (§3), honored when reading old epochs and never minted anew. A base blob wider than 136 bytes is a form this revision predates: a recipient reads the root from its frozen 72-byte prefix, `control_pk` from bytes 72 to 104, and `control_root` from bytes 104 to 136 only when it derives to that `control_pk`, and whatever the extra bytes govern stays frozen until it updates, so a new form never forks an older client off the Community. Any other width is malformed and the blob is dropped. The scope and epoch live *inside* the ciphertext, and a recipient verifies both against the event's tags before accepting the key, making a blob unspliceable; a staff recipient additionally requires that `new_control_root` derive to exactly `new_control_pk` (CORD-02 §5), refusing a mismatched pair rather than adopting a plane split from its readers. The wrap key is the NIP-44 conversation key between the Rotator and the recipient — one ECDH either side can compute, so a NIP-46 bunker account opens its blob with a single nip44_decrypt, no raw-key access needed.

Three more scopes bind blobs that only ever ride a delivery (below), and the blob's scope id binds which (CORD-03): a restricted Channel's **writer scope**, `sha256("concord/writer-scope" ‖ channel_id)`, and **certifier scope**, `sha256("concord/certifier-scope" ‖ channel_id)`, whose 72-byte blobs carry a writer epoch's secret and its certifier's secret in the Channel shape, `scope_id[32] ‖ epoch_be[8] ‖ secret[32]` (CORD-03 §1); and a Channel's **history scope**, `sha256("concord/history-scope" ‖ channel_id)`, whose 104-byte blobs carry an earlier epoch's Chat Plane address and *conversation key*, never its secret, as `history_scope[32] ‖ epoch_be[8] ‖ address[32] ‖ conv_key[32]` (CORD-03 §5).

**Deliveries are not rotations.** A 3303 rumor carrying `["delivery", "<form>"]` hands keys to members who are owed them (CORD-03 §5) and is never a rotation: it doesn't advance an epoch, and nothing it omits removes anyone from reading (a writer epoch's minting delivery decides only who may later be served there, CORD-03 §1). A delivery rides a Channel's access plane under an encrypted seal, its content the same blob array, and carries exactly these tags, with no `prevepoch`, `prevcommit` or `chunk`:
```jsonc
"tags": [
  ["scope",    "<hex>"],                  // the Channel's id32, or its writer, certifier or history scope
  ["newepoch", "<decimal>"],              // the epoch whose key it delivers
  ["delivery", "access"],                 // or "history", for read-only history (CORD-03 §5)
  ["writer",   "<hex>"],                  // OPTIONAL, writer and certifier scopes: the pubkey the delivered secret derives to
  ["cert",     "<recipient hex>", "<signature hex>"],  // OPTIONAL, repeated: a writer certificate (CORD-03 §1)
  ["mint",     "<part>", "<parts>"]       // OPTIONAL: part of a writer epoch's minting delivery, counted from 1
]
```
Writer and certifier secrets travel as form `access`, their scope telling them apart. A delivery carries at most 80 blobs, 60 of the 104-byte history form and 48 when it hands out certificates, and a reader accepts up to 120. The caps are measured, not chosen: 80 of the wider forms push the rumor past a NIP-44 padding step, which carries through the seal to about 77 KB, while 60 stay near 55 KB, so each cap keeps one event inside a 64 KB relay limit. A client MUST treat a 3303 whose `delivery` form, or blob width, it doesn't understand as carrying no removal verdict for itself, so a later revision can deliver keys in a new shape without an older client reading it as being cut out.

## 2. Receiving & Processing Rekeys

A receiver detects whether they've been removed from the channel or community; the client then either visibly removes them or switches to the new keys (a new epoch).

**Subscription.** Rekeys arrive in real-time by precomputing the next rekey address:
```jsonc
{
  "kinds": [1059],
  "authors": [
    // per PRIVATE Channel you hold; the NEXT channel-epoch's rekey address, under
    // the community_root you hold and every earlier root you still hold:
    group_key("concord/rekey-pseudonym", root, channel_id, channel_epoch + 1).pk,
    // and the next base-rotation address, under the community_root you hold:
    group_key("concord/base-rekey-pseudonym", community_root, community_id, root_epoch + 1).pk
  ]
}
```

A Channel rotation is addressed under the `community_root` its recipients held when it was minted: the current root for a standalone Rekey, the prior root for one riding a Refounding (§3). A receiver that adopts a base rotation before that Refounding's Channel rotations reach it finds them only under the root it held before, so a client looks for each Private Channel's next epoch under every root it has held since it last advanced that Channel.

Each key blob has a **locator**, derived from the Rotator's and recipient's public keys plus the rotation scope and epoch:
```
locator = hkdf(rotator_xonly || recipient_xonly, "concord/recipient-pseudonym", scope_id, epoch)
```

To check if you are part of a rekey, compute your locator and search for it within **all rekey events**, and you **must** validate the rekey came from a role-authorized administrator before accepting it. A rotation to many recipients spans several events, each tagged `["chunk", i, n]` (1-based) and correlated by the Rotator (the seal's npub), the scope, one `newepoch` and one `prevcommit`, so two Rotators concurrently rekeying the same epoch never merge into one set. A Rotator MAY extend a rotation, at the same `newepoch` and `prevcommit`, with chunks numbered past the original `n` declaring the new total; a reader unions every chunk's blobs, including two chunks claiming one index, and holds a complete set only at every index up to the largest `n` any chunk declares:
- If any chunk contains your locator and its blob opens, decrypt the new keys and shift to the new epoch; no other chunk is needed.
- Only once you hold **all `n` chunks** and none contains your locator have you been removed, and only by a Rotator that holds the rotation's bit and strictly outranks you. A missing chunk is never a removal: the client refetches until the set is complete before concluding anything.
- A rotation carrying no blob removes nobody, and a blob at your locator that won't open is never a removal. A non-owner rotation without a `vac`, or citing a Grant not yet synced, waits (CORD-04 §5). A non-owner base rotation with no blob for the owner, or for a Grant holder its Rotator can't act on with `BAN`, is neither adopted nor read as a removal by anyone.

The locator derives from *public* inputs on purpose, and it leaks nothing an outsider can reach: the locator list lives inside the encrypted event, the Rotator's npub is sealed, and channel ids are never public, so only a key-holding member can compute or search a locator. A member *can* confirm a fellow member's presence in a rotation — information members effectively hold anyway (the member list, Banlist, and Guestbook are all member-visible) — and the trade buys something real: a locator computes from public keys alone, so a NIP-46 bunker account finds its blob without touching a raw private key.

Before adopting a new key, a receiver must also verify **continuity**: recompute the epoch-key commitment (CORD-02, A.5) over the key it currently holds and require it to equal the event's `prevcommit`, with all chunks of one rotation carrying identical continuity fields. A match proves the rotation extends the very key you hold; a mismatch with a higher `prevepoch` means you missed a rotation (fetch the gap first); any other mismatch is a fork or garbage, reject it. One exception: a Channel rotation committing to `(prevepoch, community_root)` is a Public Channel made private (CORD-03 §2), and extends the chain for a holder of an earlier private era's key as well. `newepoch` MUST be `prevepoch + 1` and the epoch the address was derived for, and a reader drops any other. A member holding no key for the scope yet has nothing to check continuity against, and adopts on authority and the blob's binding alone. `prevcommit` is a convergence check, not a secrecy mechanism — post-removal secrecy rests entirely on a removed member receiving no blob; `prevcommit` just keeps honest members advancing along one shared chain.

## 3. Refounding

A Refounding is a deep whole-Community rekey, performed when banning a member from a Private Community or when converting a Public Community to Private:
- The Refounder prepares a compaction of the current Control Plane into a new, slim representation. If the Refounder cannot reliably fold all Control events, the Refounding must be aborted. Its fold must settle (the Roster fold reaching its single answer) or the Refounding aborts. It carries the head its own fold decides for every entity, settled on before or not: where the fold steps down from a refused head, the edition it steps down to, and nothing for an entity settled as absent. A head the Refounder keeps only because it settled on it before the Roster came to refuse it (CORD-04 §1) is carried as a reader holding no floor folds it, and only when the Refounder's own fold admits that edition too; otherwise nothing is carried for it, never the refused head as if it stood, since the new epoch would read it on its own and admit it.
- The `community_root` is rolled, and a fresh `control_root` is minted alongside it (CORD-02 §2). The pair travels in the same base blobs (§1) — every member receives the new `control_pk`, staff also the secret — so converging on a base rotation converges both.
- The compacted Control Plane is republished at the new epoch's Control address — signed by the new `control_root`-derived signer, readable under the new `community_root` (CORD-02 §5) — only after confirmed publication of the root roll.
- Every Private Channel the Refounder holds a key for is rekeyed, each sealed and addressed under the **prior** `community_root`, never the freshly minted one (Public Channels rotate with the base for free, CORD-03). This matters under a race: if two Refoundings collide, the base converges on one winner and the losers drop their new roots, so a channel rekey sealed under a *new* root would be unreadable to every base-fork loser; sealing under the shared prior root keeps it openable on either branch.
- Duties other CORDs give the Refounder ride along: the compaction carries a Channel sync's predecessor beside its head (CORD-04 §8); every restricted Channel's live writer epoch retires with the root, so the Refounder (failing them, any manager) mints a fresh one for the writers who remain, its ledger stopping, with `from`, the members CORD-03 §1 says a closing mint stops; and the Refounder re-issues each running Timeout it could issue itself, dated as first issued (CORD-04 §8).
- The new epoch's Guestbook is seeded with a membership snapshot (CORD-02 §5), a best-effort final step — a Refounding succeeds with or without it.

After a Refounding, the Control Plane shrinks back to its smallest size by trimming prior history into a snapshot of the prior epoch's state: the last Control Plane state is simply rewrapped, and because Control Plane seals are plaintext (CORD-02 §5), the re-encryption under the new epoch preserves the original authors' signatures, verifiable by a fresh joiner.

Compaction keeps Refoundings fast and asynchronous: members hop across dozens of epochs with thousands of Control events without reprocessing the entire Control Plane each time.

**Authority.** A standalone Channel Rekey requires `MANAGE_CHANNELS`. A Refounding requires `BAN`, and so do the Channel rotations riding it: a reader honors a Channel rotation from a `BAN` holder whose base rotation it adopted, the Refounder, without `MANAGE_CHANNELS`, so a moderator who bans cuts the banned member from every Private Channel at once. In both, the Rotator must strictly outrank every removed target (CORD-04). A receiver verifies the seal's real npub against its folded Roster before honoring anything, and a rotation cites the Grant it acts under like any authority action (CORD-04's `vac`), so a just-demoted admin's rotation is never honored by a lagging client. Holding a key is never authority: a removed member still holding the prior root — or a demoted staffer still holding the `control_root` (CORD-02 §2) — can *construct* a perfectly shaped rotation or edition, and every honest member opens the seal, folds the Roster, and drops it.

**Rotation duties.** A rotation leaves sealed things under a key some members never held, so the Rotator re-seals them under the new key: the Pin List (CORD-04 §7) and a Private Channel's metadata (CORD-03 §2). Any member holding the bit and the key MAY do it as a backstop after a short random delay. A Rotator MUST NOT re-seal what it couldn't read.

**Failure and races.** A Refounding is resumable, not atomic: every step is idempotent (re-publishing a compaction re-wraps the same signed heads, re-sending blobs re-delivers the same keys), so a crashed Refounder simply resumes. Mid-gap, the community degrades gracefully: existing members keep their old Control fold and already hold the new root; only a fresh joiner waits on the re-anchor. The state being rotated is acquired in full *before* the first publish, so a mid-flight failure never leaves half a rotation as the only copy.

Two rotations racing to the same epoch converge deterministically: among authorized candidates at the same continuity point, the lexicographically lowest new *base* key wins — the `control_root` pair rides the winner's blobs (§1), never compared — every client computes the same winner, and a losing Refounder re-issues anything only its branch knew (its fresh channel keys) on the winning chain, its own minted pair dropped with its root. A client converging onto a sibling adopts all the sibling's rotation carries, as if it had adopted it first: its control pair, its `sever` mark and its Rotator as the epoch's snapshot authority. Two Channel rotations racing to one channel epoch converge the same way, on the lowest new Channel key. A client MAY keep the losing fork's key to read what was sent into it. The same-epoch heal is **down-only** — a held epoch re-converges solely to a strictly lower sibling, so a flaky fetch that returns only the higher sibling can never re-fork a settled epoch.

**Upgrading a legacy Community.** An epoch minted before the `control_root` split (CORD-02 §2) keyed the Control Plane by the member-held legacy derivation, which every client retains for reading such epochs (CORD-02 §5). The upgrade is not a new mechanism, it is the next Refounding: a compliant Rotator performing any base rotation MUST mint the split — a fresh `control_root` beside the new root, delivered in the §1 blob widths — so a private Community upgrades as a side effect of its next ban, with nobody deciding to. The epoch is the version boundary and the blob width the signal, no version field needed (CORD-02, Appendix B): a 104- or 136-byte base blob announces an upgraded epoch, while a 72-byte one is the legacy form, never minted by a compliant Rotator. A reader honors a 72-byte base blob at any epoch, folding that epoch's Control at the legacy address, and SHOULD warn when that downgrades a split Community. A Public Community may go years without a ban, so a client SHOULD offer staff a deliberate upgrade Refounding; until one lands, the plane stays exactly as writable as it always was — the pre-split status quo, never worse.

Stale software degrades honestly, in two grades. A legacy client that reads its base blob leniently — the legacy layout is a strict prefix of the new — still extracts the new `community_root`: membership and every Chat plane survive, and only its Control fold freezes at the boundary epoch, a safe prompt to update, since a frozen fold can be starved of new state but never fed forgeries. One that enforces the old 72-byte width drops the blob and parks at the prior epoch entirely, the same experience as a missed rotation. Either way a staffer on stale software cannot write at the new address at all, so staff update first — the Refounder's client, by definition, already has. What a Rotator MUST NOT do is mirror editions to the new epoch's legacy-derived address to appease stale readers: the mirror re-opens exactly the member-writable surface the split closes.

**Severing Refoundings.** A Public Community's door is its live invite links (CORD-05 §2), and a link survives rotations by design: its creator re-posts the bundle behind the same coordinate, so fresh keys reach whoever still holds the URL. That's exactly wrong when the rotation is a containment, when the members being removed came in through that door: the Refounding rolls the root, every honest creator's client refreshes its links into the new epoch, and the removed party fetches the bundle again and walks back in. Retiring the links isn't the Rotator's to do either, since a link's revocation tombstone takes that link's `signer_sk`, which only its creator's Invite List holds (CORD-05 §4), so the authority to rotate and the ability to close the door sit with different people, and only the rotation reaches everyone.

A Rotator MAY therefore mark a base rotation a **Severing Refounding** with `["sever", "1"]` on every chunk. Its only value is `"1"`, and a chunk carrying any other value, or the tag twice, is malformed and refused, it means nothing on a Channel scope, and a receiver that reads it from any chunk applies it to the whole rotation, so an unmarked chunk can't launder it away. A client adopting a severed rotation SHOULD publish a revocation tombstone (CORD-05 §2) for every public link it created for that Community under an epoch older than the one the rotation opens (its Invite List `epoch`, CORD-05 §4), and MUST NOT refresh such a link into the new epoch. A link minted at that epoch or later is untouched: that's how a Community re-opens on purpose after a containment, and why a second device adopting the rotation late never retires a door someone opened since. An entry with no `epoch` reads as epoch 0 (CORD-05 §4) and is retired with the rest.

The tag asks, it can't retire anything itself: a creator running software that doesn't know it, or declining, keeps vending its bundle, so a Severing Refounding closes exactly the doors whose creators cooperate, as each one's client adopts. In the gap a stale bundle still resolves, but it vends the superseded root, so whoever joins through it lands on a dead epoch and reads nothing an honest member writes. `sever` confers no authority: it rides a rotation the receiver has already judged in full (Authority, above: a Refounding takes `BAN`), so one from a member without it goes with the rotation that carried it. One consequence is deliberate: a `BAN` holder can, through it, retire the owner's links for good, and a Community that doesn't want that shouldn't grant `BAN`. Retiring the last live link flips a Community to Private as usual (CORD-05 §2), the Severing Refounding being the Refounding that takes, so nothing further rotates.
